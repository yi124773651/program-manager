# Windows Defender 误报改进计划书

## 1. 文档信息

- 项目：程序管理器（Program Manager）
- 当前版本：1.1.8
- 编制日期：2026-08-19
- 适用范围：Windows 发布包、Tauri/Rust 后端、场景动作、系统集成和发布流水线
- 计划状态：执行中，代码整改已完成第一轮，默认发布链路不强制签名，干净环境复测尚未完成
- 当前结论：现象更符合未签名二进制叠加自动化能力后的机器学习误报风险；本项目接受默认无签名发布的运营取舍，因此重点转为降低行为风险、固定产物哈希并完成 Defender 复测，不能仅以“误报”结案

## 2. 背景与问题结论

### 2.1 已确认的检测事件

Defender 事件日志记录了以下检测：

- 检测名：`Trojan:Win32/Bearfoos.A!ml`
- 威胁 ID：`2147731250`
- 检测类型：快速路径
- 检测来源：实时保护
- 文件路径：`D:\soft\程序管理器\program-manager.exe`
- 处置结果：隔离
- 检测时间：2026-08-19 07:40:12
- 状态变更时间：2026-08-19 07:40:47
- Defender 产品版本：`4.18.26070.9`
- 安全情报版本：`1.457.235.0`（更新时间：2026-08-19 03:06:59）
- 当前本地 release 主程序 SHA-256：`EB0C575978837924F8CC89AC9ECB4F0439DC5354692EAF8A6557E5FB2A77D232`
- 当前本地 release 主程序签名状态：`NotSigned`

其中 `!ml` 表示机器学习泛化检测，不等同于发现了明确的木马签名。该结论只能说明检测依据偏向模型判断，不能替代代码审查和行为验证。当前安装目录中的主程序已经被隔离，现场卸载器检查结果为未签名。

### 2.2 主要诱因

1. 基线发布流水线没有配置 Windows Authenticode 签名，主程序、安装器和卸载器缺少可信发布身份；根据当前决策，默认发布继续允许无签名。
2. 基线版本曾在隐藏窗口中调用 PowerShell 执行网络请求、启动程序、管理员提权、按键模拟和窗口枚举。
3. 基线版本的 `execute_action_template` 接收脚本字符串并直接交给 PowerShell 执行，形成通用脚本执行入口。
4. 基线版本会写入用户注册表右键菜单，并开放较宽的 Tauri Shell、文件系统和资源访问权限。
5. 上述行为单独看均有业务解释，但组合后与自动化工具、脚本加载器和远程控制类程序存在相似静态特征；第一轮整改已移除其中的大部分高风险实现，仍需完成发布和实机验证。

### 2.3 当前未发现的行为

静态检查未发现以下典型恶意模式：

- 进程注入 API，如 `CreateRemoteThread`、`WriteProcessMemory`、`VirtualAlloc`；
- `Run`、`RunOnce` 启动项或计划任务持久化；
- 下载可执行文件后自动运行；
- 明显的自解压、二进制混淆或远程载荷加载。

因此本计划按“降低误报概率并同步改善安全边界”执行，不将当前检测直接认定为真实木马，也不以关闭 Defender 或添加排除项作为解决方案。

## 3. 改进目标

### 3.1 必达目标

- 每个发布产物均生成可追溯的版本、提交号、构建时间和 SHA-256 清单；签名作为可选增强，不作为默认发布条件。
- 默认业务路径不再通过 PowerShell 执行固定功能。
- 移除通用脚本执行入口，改为受控动作类型和结构化参数。
- 收紧 Tauri capability、资源协议和网络访问范围。
- 建立发布前 Defender 验证、哈希记录和误报申诉流程；若某次发布启用签名，再额外执行签名验证。

### 3.2 非目标

- 不在本计划中禁用或绕过 Defender。
- 不为了降低误报而删除必要的程序管理功能。
- 不在没有替代实现和回归测试的情况下直接移除场景能力。
- 不把第三方扫描平台结果作为唯一安全结论。

## 4. 风险分级与处理顺序

| 优先级 | 风险 | 现状 | 处理要求 |
|---|---|---|---|
| P0 | 发布包无签名 | 已确认且已接受 | 默认允许无签名；通过哈希清单、行为整改和 Defender 复测降低风险，签名保留为可选增强 |
| P0 | 通用 PowerShell 执行 | 已确认 | 限制为受控动作，默认路径移除 PowerShell |
| P1 | 管理员启动、窗口控制、按键模拟组合特征 | 已确认 | 改用结构化 API，并增加明确确认和审计 |
| P1 | Shell、文件系统和资源权限过宽 | 已确认 | 按命令和目录收紧 capability 与 scope |
| P1 | 运行时输入拼接脚本 | 已确认 | 禁止用户输入直接进入脚本源码 |
| P2 | 误报复现和申诉材料不完整 | 待建立 | 固化构建、哈希、签名和 Defender 事件证据 |
| P2 | 未来签名方案缺失 | 当前不启用 | 默认发布不依赖签名；若未来需要签名，单独设计并验证完整签名链路 |
| P2 | NSIS 卸载器可能是安装器内嵌对象 | 已记录 | 仅在未来启用签名时验证独立卸载器或保存 NSIS 安装器签名覆盖证据 |

## 5. 分阶段实施计划

### 阶段 0：样本与证据固化（基本完成）

目标：保证后续整改能够证明“哪个版本、哪个构建产物、哪个行为”触发了检测。

任务：

- [x] 保存当前检测事件的时间、检测名、威胁 ID、文件路径和处置结果。
- [ ] 从正式发布产物或构建记录获取主程序、安装器、卸载器的 SHA-256；当前仅完成主程序基线哈希。
- [x] 记录 Windows Defender 产品和安全情报版本；Node、Rust、Tauri CLI 版本需在 CI 清单中补齐。
- [x] 为每次发布生成版本清单，包含 Git 提交、构建时间、产物哈希和签名状态；正式清单随 Release 上传。
- [x] 不恢复或运行已被隔离的未知样本；后续复测使用可追溯的新构建产物。

验收：能够根据版本号和哈希唯一定位每一个待测文件。

### 阶段 1：记录发布身份状态（默认不启用签名）

目标：默认发布不依赖 Authenticode 签名；manifest 如实记录签名状态，为未来可能的外部签名方案保留数据接口。

任务：

- [x] 移除默认 Tauri `signCommand` 和 CI 签名验证步骤，构建不依赖 PowerShell 或签名凭据。
- [x] 发布附件提供 manifest，记录实际签名状态；无签名时明确记录 `NotSigned`，不得伪造签名信息。
- [ ] 若未来需要签名，重新选择证书方案并在独立分支设计、验证和维护签名链路。

验收标准：

- 默认发布只要求产物存在、版本一致、SHA-256 可追溯；不执行签名验证。
- 若未来显式启用签名，才要求 `Get-AuthenticodeSignature` 对主程序、安装器及实际存在的独立卸载器返回 `Valid`，并由独立门禁验证签名覆盖；
- 无签名发布的 manifest 必须记录签名状态为 `NotSigned`；安装器和安装后的主程序哈希均有记录。

### 阶段 2：移除默认路径中的 PowerShell

目标：降低静态特征和行为特征，同时保持现有功能。

任务：

- [x] 网络图片获取改用 Rust HTTP 客户端，限制 HTTPS、响应大小、内容类型和重定向次数。
- [x] GitHub 更新检查改用 Rust HTTP 客户端和固定 API 地址。
- [x] 程序启动改用结构化进程 API，不再通过 `cmd /C start`。
- [x] 管理员启动改用明确的 Windows Shell API 封装，参数不拼接 PowerShell 文本。
- [x] 进程检测改用 Windows 进程枚举 API，不再调用 `tasklist`。
- [x] 窗口查找和按键功能改用 Rust/Windows API 封装，保留必要的用户确认。
- [x] 通知功能改用原生通知库或 Tauri 插件，避免拼接 Toast PowerShell 脚本。

验收标准：

- 默认启动、更新检查、图片获取、场景执行路径不启动 `powershell.exe`；
- 用户输入不会作为脚本源码传入外部解释器；
- Windows 功能测试覆盖启动、提权、窗口等待、按键、通知和进程关闭。

### 阶段 3：替换通用脚本执行入口

目标：消除可被视为脚本加载器的通用执行能力。

任务：

- [x] 删除或封闭 `execute_action_template(script_content, ...)` 对外暴露的通用脚本接口。
- [x] 定义固定动作枚举，例如启动程序、打开 URL、打开文件夹、复制路径、关闭进程、发送通知。
- [x] 每种动作只接收结构化参数，不接收 PowerShell 代码。
- [x] 对 URL、文件路径、进程名、按键字符串进行格式和长度校验。
- [x] 管理员运行、结束进程和发送按键等高风险动作增加明确确认，并在前端持久化审计及 Rust 追加式日志中记录结果。
- [x] 旧版本动作配置按固定动作白名单清洗；脚本字段、未知动作和非法参数标记为禁用，不自动执行。
- [x] 清洗结果仅在内容发生变化时回写；回写前创建单文件可恢复备份，并测试重复启动的幂等性。

验收标准：

- 前端和后端均不存在业务层脚本模板拼接；
- 导入旧配置不会执行其中的任意脚本内容；
- 动作执行日志包含动作类型、目标、结果、退出码和错误信息；
- 单元测试覆盖恶意引号、换行、超长参数和非法路径。

### 阶段 4：收紧 Tauri 安全边界

目标：减少被利用时的可用权限，并降低静态审查风险。

任务：

- [x] 移除未使用的 `shell:allow-execute`，仅保留明确需要的 Shell 能力。
- [x] 将文件系统权限限制到应用配置、图标和备份目录，避免使用默认全量权限。
- [x] 将 `assetProtocol.scope` 从 `**` 收窄到实际资源目录。
- [x] CSP 网络范围只保留必要的 HTTPS 域名；禁止默认允许任意 HTTP。
- [x] 背景图片仅允许 Picsum/Unsplash 固定 HTTPS 域名并逐跳校验重定向；更新地址仅允许 GitHub 固定域名。
- [x] 右键菜单仅写入固定 HKCU 路径，程序路径要求真实绝对 EXE，注销操作保持幂等。

验收标准：

- capability 文件只包含业务实际使用的权限；
- 未授权目录读取、任意 Shell 执行和任意网络请求均被拒绝；
- 安全测试覆盖路径穿越、非法 URL、导入包路径和注册表边界。

### 阶段 5：发布验证与误报申诉（外部条件未满足）

目标：证明整改后的发布包可安装、可运行且不再触发当前检测。

任务：

- [ ] 使用最新 Defender 安全情报执行文件扫描和实时启动测试。

- [ ] 检查主程序、安装器和卸载器（如存在）的哈希；签名状态仅作记录，不作为默认阻断条件。
- [ ] 对实际拟发布版本向 Microsoft Security Intelligence 提交误报申诉。
- [ ] 将申诉编号、提交哈希、版本号和处理结果归档到发布验收记录。

验收标准：

- 版本、测试、哈希和安装验证门禁通过后才允许创建 Git tag 和 GitHub Release；默认不增加签名门禁；
- 若仍被检测，暂停发布并保留样本、日志和哈希，进入专项分析。

## 6. 发布流水线门禁

后续正式发布必须按以下顺序执行：

1. 版本一致性检查。
2. 前端测试、Rust 测试、格式检查和构建检查。
3. 生成产物并记录 SHA-256；默认产物可以未签名。
4. 生成发布清单，记录实际签名状态；不要求签名验证。
5. 在隔离 Windows 环境执行安装和启动烟测。
6. 执行 Defender 检查并保存事件结果。
7. 生成发布清单后再创建 tag 和 Release。

任何哈希不一致、版本不一致、安装失败或 Defender 隔离事件都必须阻断发布；签名未配置不阻断默认发布。

发布清单至少包含以下字段：`version`、`commit`、`builtAt`、`artifacts[].path`、`artifacts[].sha256`、`artifacts[].signatureStatus`、`artifacts[].signer`、`artifacts[].timestampSigner`。其中 `timestampSigner` 表示 RFC 3161 时间戳证书主体，实际签名时间应同时保留在签名验证日志中。

## 7. 回滚与兼容策略

- 阶段 2 和阶段 3 采用分阶段合并，保留旧功能的明确禁用开关，不保留无限期的任意脚本执行后门。
- 旧版本配置只做数据迁移，不自动执行旧脚本。
- 若 Windows API 替代实现尚未完成，先保留功能分支进行测试，不将未通过行为和安装验证的包发布给用户。
- 构建日志、产物哈希和申诉材料单独备份，避免发布链路失去追溯能力。

## 8. 后续决策点

以下事项需要在进入正式发布前确认：

- 是否继续支持用户自定义 PowerShell 脚本；计划建议默认移除，仅保留受控动作。
- 是否需要管理员启动和按键模拟；若保留，应作为显式高风险功能单独授权。
- 未来是否重新采用组织代码签名证书还是 Azure Trusted Signing（当前不作为发布前置条件）。
- 是否将更新检查和图片获取统一迁移到 Rust 网络层（代码迁移已完成，剩余固定域名策略确认）。
